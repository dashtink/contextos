# Plan: agent-led updates for existing vaults

**Goal:** a user says "update ContextOS" and an agent upgrades their vault to a new release with no manual file work, no lost personal data, and no silent overwrites of their customizations.

**Based on:** a review of `template/` at v0.2.0. I could not see any user's live vault, so the migration path (section 5) is designed from the old template and will need a dry run against the first real vault.

## 1. What breaks updates today

| Problem | Files |
|---|---|
| Hybrid files mix system text with personal data | `contextos-core.md`, `_architecture.md`, `_rules-tagging.md`, `_context-registry.md`, `_rules-sensitive.md` |
| Placeholder files become personal after setup, so the template can't overwrite them | `_persona.md`, `_voice-guide.md`, `_ops-layer.md`, `_docx-style-guide.md`, `Daily/*`, `personal-ops/*` |
| Users edit rituals in place, so the update can't tell whose text is whose | all `ritual-*.md`, `templates/*` |
| No record of what was installed | no version or hashes in the vault |
| Nothing machine-readable says what changed | prose-only `CHANGELOG.md` |
| Domain list and projects are duplicated in the core file, architecture and projects index | drift, and a three-way merge nightmare |

## 2. Design

### 2.1 File ownership classes (the core idea)
Every template file gets one class in `template/manifest.json`:

| Class | Update behavior | Examples |
|---|---|---|
| `system` | If the vault copy matches its installed hash, replace silently. If the user edited it, three-way merge (installed version, vault copy, new version) and ask only on real conflicts. | rituals, most rules, templates, `_why.md`, `_persona-guide.md`, `_source-adapters.md`, `_architecture.md` (after split) |
| `personal` | Never touched. | `_persona.md`, `_profile.md`, `_domains.md`, journals, People, meeting notes, domain context and logs, `wins.md`, `Daily/*`, `_change-log.md` |
| `seed` | Created only if missing; never overwritten. | `.obsidian/*`, `Bases/*`, folder READMEs, `_ops-layer.md`, `_docx-style-guide.md`, `_voice-guide.md` |
| `retired` | Moved to `x_archive/`, never deleted. | files removed in a release |

### 2.2 Split the hybrid files (a one-time template change, v0.3.0)
| Today | Becomes |
|---|---|
| `contextos-core.md` (persona name, user, key IDs, domain map, projects snapshot, plus routing and rules) | `contextos-core.md` (**system**: routing table, session start, core rules) plus `_profile.md` (**personal**: who you are, assistant name, key IDs). The domain map and projects snapshot are dropped; the core points to `_domains.md` and `_projects-index.md` as the single source of truth. |
| `_architecture.md` (vault map and tag namespaces, plus domain index and drift log) | `_architecture.md` (**system**) plus `_domains.md` (**personal**: domain index, drift log) |
| `_rules-tagging.md` (namespaces plus user-added tags) | `_rules-tagging.md` (**system**) plus `_tags-custom.md` (**personal**). `domain/*` tags are derived from `_domains.md`. |
| `_context-registry.md` (thresholds plus tracker table) | `_context-registry.md` (**system**: thresholds) plus `_data/_context-tracker.md` (**personal**) |
| `_rules-sensitive.md` (default list plus user additions) | `_rules-sensitive.md` (**system**) plus `reference/_never-store.md` (**personal**) |
| `router.md` | stays as is; the only thing pasted into Claude |

### 2.3 Protect user customizations of system files
- Every ritual and rule ends with a marked block: `<!-- local:start --> ... <!-- local:end -->`. Anything inside is preserved verbatim on update. Customizing there makes updates mechanical instead of a merge.
- User-created rituals go in `z_contextos/rituals/custom/` with their own `_rituals-custom.md` index. The core file tells the assistant to read both indexes.
- Edits outside the local block are still allowed; they're detected by hash and merged (2.1).

### 2.4 Installed-state record
`z_contextos/system/_template-state.json`, written at setup and rewritten by every update:
```json
{ "template": "dashtink/contextos", "version": "0.3.0", "installed": "2026-10-21",
  "files": { "z_contextos/rituals/ritual-morning.md": { "sha256": "…", "status": "stock|customized" } } }
```
It tells the agent which files are untouched and what the exact base version is, and makes a partial update resumable.

### 2.5 Machine-readable releases
- `template/manifest.json`: every file, its class, its sha256. Generated by `scripts/make-manifest.sh` (replaces `MANIFEST.txt`), checked in CI so no file ships unclassified.
- `upgrades/<version>.md`: one file per release with a YAML block of operations (`add`, `replace`, `merge`, `rename`, `retire`, `manual`), plus short prose explaining why. The agent reads operations, not prose.
- Git tags `vX.Y.Z` so the agent can fetch the exact old and new versions. (Raw GitHub at a commit SHA also works.)
- Semver: patch = wording and fixes, minor = additive, major = structural change that needs a migration.

### 2.6 The update flow (`UPDATE.md`, plus `ritual-update.md` in the vault)
Trigger: "update ContextOS". `ritual-update.md` (system) holds the repo URL and points the agent at `UPDATE.md`.
1. **Detect:** read `_template-state.json` (or enter adopt mode, section 5). Fetch the latest release and every `upgrades/*.md` between the two versions.
2. **Plan (dry run):** classify each file as replace, merge, add, rename or retire. Show one table. Flag anything touching a customized file. **Wait for approval.**
3. **Back up:** copy every file it will touch to `z_contextos/x_archive/pre-update-vX/`. Offer `git init` on the vault as an optional extra safety net.
4. **Apply:** one file at a time, read before write, `personal` class never written. Update the state file after each file.
5. **Verify:** run `ritual-setup-check`, extended to compare the vault against `manifest.json`.
6. **Log:** entry in the vault `_change-log.md` (what changed, from and to version), and a rollback note pointing at the backup folder.
7. **Remind** of manual steps listed in the release's `manual` ops. The only recurring one is re-pasting `router.md` when it changed, which should almost never happen.

Safety properties: no deletes (retire moves to `x_archive/`), idempotent (safe to re-run after a failure), merges never silently drop either side, approval gate before any write.

### 2.7 Passive nudge
Morning checks the latest release tag about once a week and adds one line to the briefing ("ContextOS 0.4.0 available — say 'update ContextOS'"). Skips silently if offline.

## 3. Maintainer release checklist
1. Bump `template/VERSION`.
2. Add `upgrades/<version>.md` and a `CHANGELOG.md` entry.
3. Run `scripts/make-manifest.sh` (regenerates `manifest.json` with hashes).
4. CI checks that every template file is classified and the manifest is current.
5. Tag `vX.Y.Z` and publish a GitHub release.

## 5. Existing vaults (installed before the state file existed)
Adopt mode handles any vault from v0.1.0 or v0.2.0:
1. **Baseline:** fetch the `v0.1.0` template (tag, or commit `c798e72`) and the `v0.2.0` template. Hash-compare every vault file to the baseline it most likely came from: unchanged = `stock`, changed = `customized`.
2. **Extract personal data out of hybrids** into the new split files (core → `_profile.md`; architecture domain index → `_domains.md`; registry tracker → `_context-tracker.md`; custom tags → `_tags-custom.md`; sensitive-list additions → `_never-store.md`). The old hybrid is replaced by the new system version only after extraction is verified by reading the new files back.
3. **Customized rituals/rules:** merge, with local edits moved into local blocks when they're clearly additive; ask when they aren't.
4. **Clean up residue:** `example-domain` references, stale `[domain-name]` rows.
5. **Add** new files (`ritual-setup-check`, `_rules-sensitive`, `_why`, `_persona-guide`, `_source-adapters`, `router.md`, folder READMEs). **Seed** `.obsidian` and Bases only if missing.
6. **Write the state file**, back up everything touched, run setup-check, log.
7. **One unavoidable manual step:** replace the old long project instructions in the Claude project with `router.md`. An agent can't edit Claude's project settings. The agent produces the filled-in router and says exactly where to paste it.

Run it first as a **dry run that only reports** (counts of stock / customized / personal-to-extract files and the planned operations). Review it before any write.

## 6. Open decisions

2. Whether local-block markers are enough, or whether users should be steered away from editing system files at all.
3. Whether to recommend git for the vault. I'd mention it as optional only.
4. Whether to ship the weekly update nudge in 0.3.0 or later.
